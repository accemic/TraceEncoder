= Enhanced features — CEDARtools.TraceEncoder extensions
:toc: macro
:toclevels: 3
:nexus-spec: https://github.com/riscv-non-isa/riscv-nexus-trace/blob/main/docs/nexus-standard/IEEE-ISTO-5001-2012-v3.0.1-Nexus-Standard.pdf

Beyond the baseline RISC-V N-Trace program- and data-trace, CEDARtools.TraceEncoder adds
a set of vendor extensions on top of the {nexus-spec}[Nexus] framework. They reuse the
standard message machinery (vendor TCODEs, reserved sync reasons,
variable-length fields) so a Nexus-aware decoder can still frame the
stream. This page describes those extensions; the wire-level definitions
are in link:../rtl/pkg/nexus_vendor_riscv_pkg.sv[`nexus_vendor_riscv_pkg.sv`]
and the registers in link:../rdl/ct_cs_cpuif.rdl[`rdl/ct_cs_cpuif.rdl`].

It also covers an alternative output path that is *not* a Nexus extension:
the 96-bit AXI-Stream export (see <<axis-output>>), which carries
instrumentation data as a plain AXI-Stream for on-chip consumers rather
than as encoded Nexus messages.

toc::[]

== Data Acquisition (DAQ) and ACT-CAP / ACT-ST

CEDARtools.TraceEncoder can export instrumentation data as **Data Acquisition** messages
(TCODE 7): an `IDTAG` plus a variable-length payload up to
`NEXUS_MSG_DATA_WIDTH` (192 bits), optionally timestamped. This carries
more than the 64 bits a standard data-trace message allows, which is why
DAQ uses a vendor payload width.

DAQ capture is driven by **ACT-CAP** (capture) / **ACT-ST** (smart
trigger). The command is written to a CPU-side RISC-V CSR,
`trActCapStCmd` at `0x0B10`:

[cols="1,2", options="header"]
|===
| Field | Meaning

| `Cmd[5:0]`         | HSI command (`trActCapStCmd_e`) — what to capture (e.g. current PC, direct data, …).
| `Sink[7:6]`        | Routing (`trActCapStSink_e`) — Nexus (ATB), AXIS, both, or TE-only.
| `DirectData[31:8]` | 24-bit auxiliary payload carried with the command.
|===

IMPORTANT: `0x0B10` is a CPU-side CSR, **not** a Wishbone register. It is
documented in the RDL only so the register exporter can describe it; the
encoder hardware does not decode `0x0B10` on the Wishbone bus.

The `Sink` routing lets the same instrumentation event go to the Nexus
trace stream, to the 96-bit AXIS instrumentation port, or both — see the
`sim-hsi-csr-cap` scenario in link:verification.adoc[Verification], which
fires the full command set and self-checks the AXIS beat.

== Filtering and watchpoints

The preprocessor (`ct_L23_preproc`) filters both control flow and data
flow before messages are generated:

* **Trace filters** (`trTeFilter[]`, from `0x0400`) — match on
  instruction type, exception/interrupt cause, and implementation-defined
  sideband to gate what is traced.
* **Comparators** (`trTeComp[]`, from `0x0600`) — primary/secondary
  address match registers for watchpoint and range conditions.
* **DF range filter** (`df` block, `0x5000-0x7FFF`) — data-address range
  filtering, evaluated as a search over the configured ranges.

These let a user restrict tracing to a region of interest, cutting trace
bandwidth at the source.

== Synchronization variants

In addition to the standard periodic and trace-enable sync, CEDARtools.TraceEncoder
defines vendor sync reasons (see link:trace-format.adoc#sync-reasons[Trace
format]):

* **`REQ_CSR` / `REQ_ATB`** — a sync explicitly requested by software via
  CSR or APB.
* **`TRACE_QUOTA`** — a sync emitted when a configured quota (number of
  trace messages or trace bytes) is reached, bounding how long a decoder
  must wait to re-synchronize.

Periodic sync is arbitrated against the actual emitted byte count: the
MSEO/MDO formatter reports bytes back to the preprocessor so sync cadence
tracks real output, not just cycles.

== Performance counters and timestamping

The `pc` block (`0x3000-0x3FFF`) provides performance counters
accumulated in the preprocessor. Timestamps are taken against the
free-running `wall_clk` and selected/configured via `trTsControl`
(`0x040`) with a 64-bit counter (`trTsCounter{Low,High}`); they ride
along as the `TSTAMP` field of sync, data and DAQ messages.

== Overflow and overrun recovery

Under sustained back-pressure (ATB stalled while TIP keeps retiring), the
internal queues can overrun. CEDARtools.TraceEncoder handles this explicitly:

* The composer injects a **QueueOverrun** condition; the encoder emits an
  **Error** message (TCODE 8, `ETYPE = QUEUE_OVERRUN`) whose **ECODE**
  bitfield records which message classes were lost (see
  link:trace-format.adoc#error-codes[Trace format]).
* On restart it emits a **`FIFO_OVERRUN`** sync so the decoder can
  re-establish position.
* A soft reset (`ct_cs_rst`) re-initializes the CSR shim so the encoder
  can be re-programmed and resume cleanly.

The `sim-overrun-recovery` scenario exercises this whole lifecycle and
hard-requires the QueueOverrun error to actually fire.

[#axis-output]
== Output: AXIS export and the ATB funnel

* **AXIS instrumentation** — a 96-bit `axis_if.master` carries
  ACT-CAP/DAQ export independent of the Nexus ATB stream, for on-chip
  sinks (e.g. a runtime-verification CPU) that consume instrumentation
  separately from program/data trace.
* **ATB funnel** (`ct_L1_funnel`) — a packet-aware merge of up to four
  ATB streams onto one output port, never switching mid-packet, for
  designs where multiple encoders (or sources) share a trace port.

=== AXIS instrumentation format

The port emits *one beat per ACT-CAP/DAQ command* routed to an AXIS sink —
there are no multi-beat packets. Unlike the encoded Nexus DAQ message, the
payload is *uncompressed*, so an on-chip consumer needs no Nexus decoder.
Each beat is self-describing: `tid` (8 bit) is the ACT-CAP command
(`trActCapStCmd_e`) and says what the payload means; `tdata` (96 bit) holds
up to three 32-bit elements packed LSB-first (element 0 in bits `[31:0]`);
and `tstrb` marks which elements are valid (four strobe bits per element,
so `0xF` / `0xFF` / `0xFFF` = 1 / 2 / 3 elements). The standard
`tvalid` / `tready` handshake applies; `tlast` is unused (single-beat).

The element layout per command (`ct_L23_preproc_composer_axis.sv`):

[cols="2,2,2,2", options="header"]
|===
| Command (`tid`) | element 0 | element 1 | element 2

| `DAQ_PC_CURR`      | current PC        | direct-data tag                    | —
| `DAQ_PC_CURR_LAST` | current PC        | last PC before exception/interrupt | direct-data tag
| `DAQ_DIRECT_DATA`  | direct-data tag   | —                                  | —
| `DAQ_DATA`         | last data value   | dtype/dsize                        | —
| `DAQ_DADDR`        | last data address | dtype/dsize                        | —
| `DAQ_DATA_DADDR`   | last data value   | last data address                  | dtype/dsize
| `DAQ_DATA_RD` / `_WR` / `IFETCH_TH` / `DATA_RD_TH` | perf-counter value (region from direct-data) | — | —
|===

The `sim-hsi-csr-cap` scenario fires every command above to the AXIS sink
and self-checks the decoded beat (`ct_axis_decoder.sv`); see
link:verification.adoc[Verification].

== Vendor configuration message

A **Vendor Config** message (TCODE 56, in the Nexus vendor range) is
*defined* to convey the encoder's configuration to the decoding device,
so a decoder could adapt to the active feature set without out-of-band
knowledge. It is **not currently emitted** — the formatter path is
stubbed (commented out) pending finalization of the payload.
