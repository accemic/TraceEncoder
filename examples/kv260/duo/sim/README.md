# `examples/kv260/duo/sim` — simulation leg of the dual-core example

One bench, migrated 2026-08-18 from the evidence archive
(`the predecessor repository, package D3b).

`tb_duo_ps_devmem` drives `duo_soc_top`'s AXI4-Lite slave exactly the way
Linux `devmem` does on the board: hold both cores, load `prog.bin` into RAM0
(MicroBlaze-V) and `prog2.bin` into RAM1 (TGC5B), configure **both** encoders
(`trTeInstFeatures.SrcID` 0/1 with `SrcBits=2`, then `trTeControl` with
`InhibitSrc=0`), clear the ring, start both cores, then turn instruction
tracing off on both and flush. It writes the merged ring to
`tb_duo_ps_devmem.atb.bin` and the golden PC sequences of both cores to
`tb_duo_ps_devmem.core{0,1}.retired.pcs`, for an offline
`NexRv -deco … -target 0 … -target 1 … -src 2` run. On top of the flow it
carries the D2/T2/U6/U9/U1 gates: DDR-sink accounting, PIB calibration and
beat balance, the DDR window lock and its read-only property, the per-core
start/stop bits, and two small unit gates on the same merged stream (URAM
one-shot at DEPTH=16, `ct_soc_ddr_sink` circular at SIZE=64 B).

## It does NOT run on the default backend

`duo_soc_top` instantiates `mbv_soc_synth_wrap` for its MicroBlaze-V half, and
that instantiates `mbv_ctrace_soc_wrapper` — generated by Vivado's
`make_wrapper` from the `mbv_ctrace_soc` block design at build time, around
the **encrypted** MicroBlaze-V core — plus the Xilinx XPM macro
`xpm_memory_tdpram`. Neither has an in-repo `.sv` source, so there is no
Verilator path for this bench. The same reasoning, the same measured error and
the full "what a re-user needs" list are in
[`../../mbv/sim/README.md`](../../mbv/sim/README.md); this bench needs exactly
the same things, plus its two program images:

* `prog.bin` — the MicroBlaze-V image, from `../../mbv/sw/build/` (the archive
  runner copied the chosen `*.bin` to `prog.bin` in the work directory).
* `prog2.bin` — the TGC5B image, from the `examples/kv260/common/tgc5b` software.

The bench loads both by those fixed names from the simulator work directory;
that behaviour is carried over verbatim rather than re-pointed, because the
choice of image is the runner's, not the bench's.

## What WAS verified without Vivado

`verilator --lint-only -Wall --timing --top-module tb_duo_ps_devmem` against
the full closure, with throwaway port-compatible stubs for the two modules
above (same technique and file order the RTL migration used):
exit 1 with **zero** real `%Error-` lines (1568 warnings; the only `%Error`
line is the aggregate `Exiting due to N warning(s)`, i.e. `-Wall`'s default
`--error-limit`, not a failure).

That run found one real migration defect, which is why it was done: the bench
instantiated **`ct_soc_trace_buf`** for its one-shot unit gate. In the archive
that was the ring; in this tree the ring is `ct_soc_trace_ring` (migration
decision A-04) and `examples/kv260/common/tgc5b/rtl/ct_soc_trace_buf.sv` is a different,
older design that kept the old name — no `oneshot_i`, `overflow_o` instead of
`wrapped_o`/`stopped_o`. The instance now names `ct_soc_trace_ring`, with the
reason written next to it.
