# Unified KV260 example CTRL window -- register model

SystemRDL source for the CTRL register window the KV260 example SoCs expose
through their PS AXI4-Lite aperture, plus the generated register block:

| File | Role |
|---|---|
| `ct_kv260_ctrl.rdl` | top file; `include`s both blocks and defines the one generated addrmap `ct_kv260_ctrl_periph` (0x00..0x38, local 0x34 an intentional gap) plus a documentation addrmap `ct_kv260_ctrl_window` showing where it sits in a top's aperture |
| `ct_kv260_ctrl/ct_kv260_common.rdl` | CONTROL / STATUS / TRACE_BEATS / TRACE_BYTES / AXIS_BEATS / TRACE_BUFSZ -- **documentation only**: every top hand-implements these in its own CTRL `always_ff` case, there is no shared RTL module behind them |
| `ct_kv260_ctrl/ct_kv260_sinks.rdl` | SINK_CTRL..DDR_BEATS, transcribed register-for-register and bit-for-bit from the real shared module [`../ct_trace_sinks.sv`](../ct_trace_sinks.sv) |
| `../ct_kv260_ctrl_regs.sv`, `../ct_kv260_ctrl_regs_pkg.sv` | generated by PeakRDL-regblock -- **never edit by hand** |

The directory and its model were added in 2026-08, while these examples were
migrated from an internal predecessor repository.

> **This is the target layout, not a description of the as-built tops.**
> Several example tops still carry the offsets they were built with; see
> "As-built drift" below. Read that section before using the generated
> register block to talk to a bitstream.

## Regenerating

```bash
make rdl-kv260          # or: bash examples/kv260/common/rdl/gen_rdl_kv260.sh
```

The script uses the same pinned virtualenv as `scripts/gen_rdl.sh`
(`rdl/requirements.txt`: peakrdl 1.5.0, peakrdl-regblock 1.3.1,
peakrdl-html 2.12.2, systemrdl-compiler 1.32.2) and prints the resolved
interpreter and every pin it checked. Commit the `.rdl` and the regenerated
`.sv` together.

`gen_rdl_kv260.sh` deliberately does **not** copy `scripts/gen_rdl_soc.sh`'s
venv lookup: that one only probes `$VENV/bin/python`, which does not exist on
a Windows checkout (`python -m venv` lays down `Scripts/python.exe`), so it
silently rebuilds the venv on every invocation. This script reuses
`scripts/gen_rdl.sh`'s fixed `find_venv_python()` instead, which probes
`Scripts/` first and additionally resolves a linked `git worktree`'s venv to
the main tree's.

The same RDL is also rendered to HTML by `make rdl-html`
(`bld/rdl-html/ct_kv260_ctrl/`, a build artifact, not committed). That
renderer carried `gen_rdl_soc.sh`'s broken venv probe until 2026-08-24 and
was therefore unreachable on a Windows checkout; it now uses the same
`find_venv_python()`, and it now covers this window at all -- its two older
maps are the TGC5B SoC peripheral map and the bare encoder CSR map, neither
of which contains these registers.

**Every declared enum must also be assigned.** A field may declare an inline
`enum` and still not use it: `encode = <type>;` is what binds the type to the
field. Without it the file compiles, simulates and reads back identically
while every exporter silently drops the value list -- no `typedef enum` in
the generated package, no value table in the HTML, `None` from
`field.get_property("encode")` for anything walking the elaborated model.
`sink_ctrl.pib_pattern` sat like that until 2026-08-24, when the doc
repository's register generator produced a table row that just stopped after
the description. `make check-rdl-encode` (`scripts/check_rdl_encode.py`, also
run by `make check-publication`) is red on any declaration nobody assigned; a
deliberate bare type anchor has to say so with `// RDL-ENCODE-EXEMPT:
<reason>` on the line above.

**Expected lint shape.** `verilator --lint-only -Wall` on the generated
regblock exits 1 with warnings in exactly three classes -- `MULTIDRIVEN`
(PeakRDL-regblock's `field_combo` struct pattern: one `always_comb` per
field, all writing different members of the same struct), `UNUSEDSIGNAL`
(`s_axil_awprot`/`arprot`, the low address bits) and `UNUSEDPARAM`. The
already-committed reference regblock generated by the same tool for the same
purpose (`examples/kv260/common/tgc5b/pkg/ct_soc_regs.sv`) exits 1 with the same three
classes. Exit 1 is therefore the accepted shape of this generator's `-Wall`
output, not a defect introduced here; port mismatches, type errors or
unresolved references would be.

## Layout decisions

**D1 -- AXIS_BEATS@0x10, TRACE_BUFSZ@0x14.** The fleet is split two ways:
`mbv`/`duo`/`trio` carry AXIS_BEATS@0x10 + TRACE_BUFSZ@0x14, the other six
tops carry TRACE_BUFSZ@0x10 + CON_BYTES@0x14. The first assignment wins
because it is the one the dashboard's `regmap.json` (`"region": "ctrl"`,
modelled on `trio_soc_top`) already treats as canonical, and because it
places the window directly before the sink block at its native 0x18 with no
gap. Cost: `mbv`/`duo`/`trio` need no change; `tgc5b2_axis_wp` moves one
register; the five-top Linux/Rocket family parks AXIS_BEATS at 0x10
(unpopulated, reads 0) and moves TRACE_BUFSZ to 0x14.

**D2 -- the sink window is `ct_trace_sinks.sv` verbatim, SINK_CTRL@0x18.**
The tops that instantiate the *real shared module* define the layout (duo,
trio, tgc5b2_axis_wp when this was decided; mbv has since joined them); the
five tops with hand-rolled copies of the same bit layout at 0x1C are the
ones that move.

**D3 -- FUNNEL_CTRL lives in the reserved CTRL index 13 (0x34)**, the gap
`ct_trace_sinks.sv`'s own header leaves to the instantiating top -- not
appended after DDR_BEATS. duo/trio/tgc5b2_axis_wp already do this;
rocket2/cva6_2 currently park it far out at 0x58.

**D4 -- everything at CTRL >= 0x3C is out of one common layout by
construction.** CON_x (console ring), WIN_ERR_x/WIN1_ERR_x (window guard),
PC/RETIRES (per-hart observation), EXT_IRQ (PLIC feed), MBOX_ERR_CNT (shared
mailbox), ATB_STALLS/ATB_BP/IRQ_DIV (mbv's backpressure generator) each exist
on a different subset of tops for reasons inherent to that top's
architecture. No fixed offset scheme serves all of them without assuming one
top's full feature set, so they stay each top's own business and are not part
of the generated addrmap.

**Why so few named fields in the common block.** Only bits with identical
offset *and* meaning on all nine tops are named (`core_run`, `trace_clear`,
`trace_wrapped`); everything else is an explicit `top_ctrl`/`top_status`
passthrough field with a doc comment. Inventing shared bit semantics across
nine designs that genuinely differ would document hardware that does not
exist.

## As-built drift

Measured from the nine `examples/kv260/*/rtl/*_soc_top.sv` CTRL case
statements and from `../ct_trace_sinks.sv` (last re-checked 2026-08-19).
Ranked by adoption cost:

| Top | CTRL 0x00-0x14 | Sink window | Extension registers |
|---|---|---|---|
| duo, trio | matches | matches | matches -- these are the reference |
| mbv | matches | matches (retrofitted; `ct_trace_sinks` instantiated) | ATB_STALLS 0x34, IRQ_DIV 0x3C, ATB_BP 0x40 -- see below |
| tgc5b2_axis_wp | TRACE_BUFSZ 0x10 -> 0x14 | matches | n/a |
| cva6_linux, cva6_linux64 | 1 move + AXIS_BEATS slot | swap own copy for `ct_trace_sinks` (behavioral, see below) | CON_x: 4 moves |
| rocket_linux | 1 move + slot | swap (same) | 4 + 7 moves (CON_x, WIN_ERR_x, EXT_IRQ, PC/RETIRES) |
| rocket2 | 1 move + slot | swap; reset value already 0x5000_0000 | 4 + 10 moves incl. FUNNEL_CTRL 0x58 -> 0x34 |
| cva6_2 | 1 move + slot | swap (same as cva6_linux) | 4 + 13 moves incl. FUNNEL_CTRL and the dual window guard |

`mbv` uses the reserved 0x34 slot for its own `ATB_STALLS` counter rather
than for FUNNEL_CTRL -- it has one encoder and no funnel, which is exactly
what "reserved for the instantiating top" means. Its `ATB_BP` register moved
off 0x38 when it adopted the window, because 0x38 is `DDR_BEATS` there; the
board campaign's `ATB_BP_OFFSET` has to match, or a
write lands on a read-only counter and silently measures "backpressure has
no effect".

Three consequences that are behavioral, not cosmetic:

1. **DDR_BASE/DDR_SIZE access policy.** In `ct_trace_sinks.sv` both are
   hardware read-only (finding U9-1: every write is discarded and latches
   `ddr_cfg_rej`). The five tops with their own sink copy accept those writes
   unconditionally, and their `ddr_cfg_rej` therefore always reads 0.
   Adopting the shared module turns the register from writable into WARL
   read-only.
2. **Reset window.** duo/trio/rocket2 reset to 0x5000_0000 + 256 MiB (address
   plan v4); cva6_linux/cva6_linux64/rocket_linux/cva6_2 still reset to
   0x6000_0000 + 64 MiB. `ct_trace_sinks.sv`'s header states the
   correspondence rule -- the RTL reset value and the devicetree
   reserved-memory window are one decision, changing one means changing the
   other. A top that adopts the shared default must have its overlay moved
   with it.
3. **Two registers appear for free** when a top swaps to the shared module:
   PIB_DROPS (the individually-wired `ct_soc_pib` instances leave `drops_o`
   open) and DDR_BEATS (not implemented in the hand-rolled copies at all).
   For a top that has no sink hardware at all, adoption is not a
   renumbering but new `m_axi_*`/`pib_*` top-level ports plus block-design
   and XDC wiring -- that was `mbv`'s case before it was retrofitted.

**Bit collisions, deliberately not resolved.** Same offset, same bit
position, different meaning per top -- harmless today because no two tops
share hardware, but a host script cannot treat these uniformly even after the
offsets are unified:

- `CONTROL` bit 2: `trace_flush` on mbv/duo/trio/tgc5b2_axis_wp vs.
  `con_clear` on the five-top Linux/Rocket family.
- `STATUS` bit 1: `axis_overflow` on mbv/duo/trio vs. `uram_stopped` on the
  five-top family (tgc5b2_axis_wp does not define the bit).

**Known stale consumer.** `examples/dashboard/regmap.json`'s `access_rule`
text for DDR_BASE/DDR_SIZE still describes the older armed-only interlock ("a
write while the sink is armed is refused, at `ddr_en=0` it is taken"). That
was superseded by the U9-1 hardening above: the register is unconditionally
read-only. The offsets in that file already match this model.
